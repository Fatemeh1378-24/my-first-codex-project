# واسط ثبت نتایج آزمون

این بسته **کد آمادهٔ انتشار** است؛ به‌تنهایی سرور منتشرشده نیست. لینک فعلی آزمون و پایگاه Supabase حفظ می‌شوند. تا وقتی آدرس واقعی در `web-preview/relay-config.js` تنظیم نشده، رفتار فعلی سایت تغییر نمی‌کند.

مسیر جدید: مرورگر شرکت‌کننده → Cloudflare Worker → جدول `public.participants` در Supabase.

## ترتیب راه‌اندازی

1. یک حساب در <https://dash.cloudflare.com/sign-up> بسازید و پلن Workers Free را نگه دارید. هیچ پلن پولی، دامنه، D1 یا اطلاعات پرداختی برای این بسته نیاز نیست. امکان ساخت حساب و دسترسی از شبکهٔ مورد استفاده باید عملاً بررسی شود.
2. در Workers & Pages، یک Worker با نام `iat-results-relay` بسازید. برای انتشار از داشبورد، محتوای کامل `worker.mjs` را در ویرایشگر Worker قرار دهید. مسیر دیگر برای فرد فنی: در این پوشه با Wrangler احراز هویت کنید و `npx wrangler deploy` را اجرا کنید؛ تنظیمات `wrangler.jsonc` شامل محدودکنندهٔ درخواست است.
3. در Settings → Variables and Secrets متغیر `SUPABASE_PUBLISHABLE_KEY` را از مقدار موجود در `web-preview/app.js` تنظیم کنید. این کلید عمداً publishable است. **از service_role یا sb_secret استفاده نکنید**؛ واسط باید همچنان تابع مجوزهای anonymous و RLS باشد. متغیر اختیاری `ALLOWED_ORIGIN` برابر `https://fatemeh1378-24.github.io` است. مسیر صفحه جزو Origin نیست.
4. در Supabase SQL Editor، فایل `supabase/relay_unique_participant.sql` را یک‌بار اجرا کنید. این فایل رکوردی حذف یا تغییر نمی‌دهد و مجوزها را باز نمی‌کند. وجود شناسه‌های تکراری قدیمی ممکن است ساخت شاخص را متوقف کند؛ در آن صورت ابتدا رکوردها را بررسی کنید. همهٔ migrationهای قبلی ستون‌ها نیز باید اجرا شده باشند.
5. Worker را منتشر کنید. آدرس واقعی چیزی شبیه `https://iat-results-relay.YOUR-SUBDOMAIN.workers.dev` خواهد بود؛ این مثال آدرس فعال نیست. بدون VPN، مسیر `/health` همین آدرس را روی وای‌فای و اینترنت همراه باز کنید. پاسخ مورد انتظار `{"ok":true,"service":"iat-relay"}` است. **این فقط دسترسی به واسط را ثابت می‌کند و آزمون ذخیره‌سازی نیست.**
6. پس از آزمون دسترسی، آدرس کامل `https://...workers.dev/results` را در `web-preview/relay-config.js` قرار دهید. تغییرات GitHub را برای انتشار آماده کنید. مقدار خالی یعنی مسیر مستقیم قدیمی Supabase؛ هنگام آزمون مسیر جدید مقدار باید واقعاً تنظیم شده باشد.
7. آزمون کامل را از GitHub بدون VPN اجرا کنید. در Network مرورگر باید درخواست به `/results` واسط برسد، نه اتصال مستقیم به Supabase. سپس مدیر پژوهش در Supabase همان `participant_id` را پیدا کند و همهٔ فیلدهای آزمون، پاسخ‌های خام SDO و MFQ و نمره‌ها را تطبیق دهد. باز شدن داشبورد مدیر با VPN مانعی برای مستقل بودن مسیر شرکت‌کننده نیست.
8. قطع اینترنت در لحظهٔ ارسال و تلاش مجدد را آزمایش کنید. همان شناسه باید فقط یک رکورد داشته باشد. بازخوانی صفحه باید پاسخ کامل ارسال‌نشده را بازیابی کند. بعد از تأیید موفقیت، دادهٔ موقت مرورگر پاک می‌شود. برای داده‌های واقعی خروجی و پشتیبان مستقل از Supabase نگهداری کنید؛ واسط جای پشتیبان نیست.

تا پایان آزمون دسترسی و تطبیق رکورد واقعی، لینک را برای جمع‌آوری پژوهش منتشر نکنید. اگر دامنهٔ رایگان workers.dev در اینترنت شرکت‌کننده‌ها قابل دسترسی نبود، این گزینه مشکل VPN را حل نکرده و باید گزینهٔ دیگری انتخاب شود.

## رفتار و محدودیت‌ها

- فقط `POST /results`، درخواست preflight و مسیر سلامت وجود دارند؛ خواندن نتایج از واسط امکان ندارد.
- مقصد Supabase و جدول در کد ثابت هستند؛ واسط proxy عمومی برای URL دلخواه نیست.
- ورودی با فیلدهای دقیق کد فعلی، سن ۲۰ تا ۴۰، پاسخ‌های پرسشنامه و حداکثر حجم ۶۴ کیلوبایت اعتبارسنجی می‌شود. نمره‌ها دوباره محاسبه نمی‌شوند؛ همان دادهٔ تولیدشدهٔ آزمون ارسال می‌شود. این اعتبارسنجی صحت پژوهشی پاسخ‌های کاربر را تضمین نمی‌کند.
- پاسخ موفق فقط پس از وضعیت موفق درج Supabase صادر می‌شود. قطع ارتباط، خطای مجوز، schema یا سهمیه، موفقیت اعلام نمی‌کنند.
- شاخص یکتا و `resolution=ignore-duplicates` باعث می‌شوند اولین ارسال یک شناسه حفظ شود و retry آن را به‌روزرسانی نکند. اصلاح رکورد موجود از این مسیر پشتیبانی نمی‌شود. مرورگر دقیقاً اولین snapshot را برای retry نگه می‌دارد.
- نسخهٔ موقت فقط پس از تکمیل پرسشنامه‌ها ساخته می‌شود؛ پیشرفت آزمون نیمه‌تمام بازیابی نمی‌شود. localStorage ممکن است مسدود، پاک یا در حالت ناشناس موقتی باشد؛ در این حالت پیام به کاربر می‌گوید صفحه را نبندد. دستگاه مشترک می‌تواند دادهٔ موقت را در معرض فرد بعدی قرار دهد؛ این قابلیت انبار دائمی یا جایگزین پشتیبان نیست.
- Origin مجاز و CORS جلوی خواندن/ارسال عادی از صفحات دیگر را می‌گیرند، اما احراز هویت یا محافظت کامل در برابر ربات نیستند؛ کلید publishable در سایت قبلی هم عمومی بوده است. نشر با Wrangler محدودکنندهٔ ۳۰ درخواست در دقیقه برای هر IP دارد. در نشر دستی، binding معادل `RESULTS_RATE_LIMITER` را تنظیم کنید یا قبل از انتشار عمومی محافظت جایگزین قرار دهید. شبکه‌های مشترک باید در آزمون ظرفیت لحاظ شوند.
- request body، headerها و اطلاعات شرکت‌کننده را در لاگ Cloudflare فعال نکنید. کد فقط وضعیت عددی خطای upstream را ثبت می‌کند. داده در مسیر از Cloudflare عبور می‌کند و همچنان در Supabase ذخیره می‌شود.
- پلن رایگان Cloudflare سهمیه دارد؛ نیاز به VPN و پایداری شبکه قابل تضمین نیست. واسط نیز توقف یا خرابی خود پروژهٔ Supabase را رفع نمی‌کند.

## بررسی محلی

```sh
node relay/relay.test.mjs
```

تست‌ها اعتبارسنجی، انتقال بدون تغییر، خطای upstream، receipt نامعتبر، قطع پاسخ پس از ثبت، ارسال هم‌زمان و بازیابی پس از reload را شبیه‌سازی می‌کنند. جایگزین بررسی رکورد واقعی در پایگاه و اینترنت ایران نیستند.

بررسی قدیمی `node web-preview/verify-preview.mjs` در نسخهٔ پایه نیز در انتظار CSS قدیمی `object-fit: contain` متوقف می‌شود، در حالی که CSS موجود `cover` دارد؛ فایل CSS یا معیار آن در این تغییر دست‌کاری نشده است.

منابع: [شروع Worker از داشبورد](https://developers.cloudflare.com/workers/get-started/dashboard/)، [سهمیهٔ رایگان Workers](https://developers.cloudflare.com/workers/platform/limits/)، [Rate limiting binding](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/).
